2 · Ce qui pousse une session à dessiner, et une version plus simple

Affirmation : aujourd'hui, quatre leviers et treize pièces, dont une seule contrainte qui s'exécute. On peut descendre à huit pièces, chaque règle écrite une fois, et confier à des mécanismes ce que la prose répète aujourd'hui en vain.

Les règles de documentation disent pourquoi, et à quel coût ; le style « visuel d'abord » dit la forme, à chaque requête ; le skill d'infographies fabrique les figures riches ; le contrôleur de documents relit le fichier écrit et oblige la session à le reprendre. Les trois premiers ne valent que si le modèle les suit, le dernier bloque.

Deux limites aujourd'hui. Le style « visuel d'abord » ne s'applique pas aux sous-agents, qui ont leur propre prompt système ; or c'est souvent un sous-agent qui compose un document. Et le contrôleur ne surveille pas les mêmes dossiers que docpin : deux définitions de « ce qui est un document » coexistent, et elles divergent depuis le 2026-10-07.

Note 1 — « peut-on rendre ça plus robuste ? et plus simple ? » Oui : treize pièces deviennent huit. Une seule description du processus, un skill que la session charge quand elle produit un document ; un vérificateur de rendu qui mesure au lieu de demander de regarder ; un contrôleur qui demande à docpin ce qu'est un document ; et les seuils écrits une seule fois, dans le code. Le détail des doublons est en section 4.

Q9 · La config de l'auteur, en attendant le plugin décidé et mis en œuvre le 2026-10-09

Oui, comme ça je me rends compte de ce que je livre. Ce qui a été fait le jour même dans la config synchronisée :
  • L'enregistreur docpin est dans la config partagée. Chaque machine l'a. Sa commande ne fait rien quand docpin n'est pas installé : [ -x "$HOME/workspace/misc/<dossier docpin>/hooks/register-on-write.py" ] && exec "$HOME/workspace/misc/<dossier docpin>/hooks/register-on-write.py"; cat >/dev/null; exit 0. Claude Code la passe à sh -c, d'où une écriture qui ne suppose pas bash. Vérifié muet sous sh et bash, docpin absent (aucune sortie, code 0, même avec 2 Mo en entrée) ; et le témoin, un faux enregistreur au même chemin, est bien atteint.
  • Pas de double inscription. La fusion des settings additionne les listes et ne dédoublonne que les commandes identiques : l'ancienne entrée locale a été remplacée par le texte exact de l'entrée partagée. Vérifié en rejouant la fusion sur des copies : une entrée après fusion, une après une seconde passe, une sur l'autre machine ; deux dans le témoin qui garde l'ancienne entrée.
  • Le skill d'infographies n'est pas ajouté. L'activer dans la config partagée le ferait télécharger sur l'autre machine (documentation officielle, page plugins/loading) : il s'y installe délibérément, à la main.
Ce qui reste manuel sur une nouvelle machine : cloner docpin dans ~/workspace/misc/<dossier docpin> et lancer uv sync ; annotate service et le linger ; installer le skill d'infographies et son Playwright (npm install && npx playwright install chromium). Quand le plugin public existera, l'auteur l'installera comme tout le monde (A1).

T1 · Où vit la règle « qu'est-ce qu'un document » (ex-Q4) décision technique

Le contrôleur de documents demande à docpin si un fichier est un document, et retombe sur les dossiers docs/ quand docpin n'est pas installé. Motif : une règle, un endroit ; les deux copies ont déjà divergé, et le contrôleur ne voit pas les dossiers que l'utilisateur ajoute dans docpin.

T2 · La boîte de réception (ex-Q7, route B) décision technique

En clair : quand la session qui a écrit le document est encore ouverte mais n'attend pas tes notes, docpin les dépose dans sa boîte de réception, et tu vois un dialogue « Approve / Deny » dans ce terminal. Claude Code ne documente pas la forme de ce dépôt : docpin imite ce que Claude Code écrit lui-même. Une mise à jour de Claude Code peut la changer sans prévenir.
Ce que montre la lecture du code : si Claude Code refuse la connexion, les notes restent à envoyer. Mais s'il l'accepte et ignore le message, docpin croit l'avoir livré : les notes passent en « envoyées » et rien n'arrive. La docstring de inbox.py dit le contraire, et la fonction unmark_sent, qui permettrait de les remettre en attente, n'est appelée nulle part.
Décision : garder la route, car sans elle une session ouverte reçoit son double dans un onglet (défaut corrigé le 2026-10-06). Trois mécanismes à poser avant le paquet public :
  • docpin retient les versions de Claude Code sur lesquelles le format a été vérifié ; chaque session ouverte annonce la sienne (champ version de son entrée de registre) ;
  • pour une version non vérifiée, docpin ne dépose rien : les notes restent à envoyer, avec le message « session ouverte, version non vérifiée : demande-lui de lancer l'attente de notes » ;
  • vérifier une version, c'est faire écrire un vrai message par Claude Code dans une socket témoin et le comparer au format de docpin, comme lors de la capture du 2026-10-06 ; et un bouton « Renvoyer » branché sur unmark_sent rattrape un envoi qui n'est pas arrivé.

T3 · La consigne de l'attente de notes, ou un monitor de plugin (ex-Q8) décision technique

On garde la consigne de l'enregistreur. Motif : elle marche, mesuré depuis le 2026-10-05. Le monitor de plugin est expérimental, ne démarre pas en mode non interactif, tournerait dans chaque session même sans document, et rien ne garantit qu'il connaisse la session. À réexaminer quand les monitors ne seront plus expérimentaux.

T4 · Ouvrir la page d'accueil sans la pastille (note 9) décision technique

Trois gestes, du moins cher au plus cher : la consigne de l'enregistreur demande à la session de te donner le lien du document dans sa réponse ; annotate open sans argument ouvre la page d'accueil, avec xdg-open ou open selon le système ; et, dans Claude Code, ! annotate open le lance sans passer par le modèle. La commande /docpin:open reste possible mais coûte un tour du modèle ; un skill seul est trop lourd ; la ligne d'état est hors de portée d'un plugin (tableau en section 7).
